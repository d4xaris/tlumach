# Специфікація функціоналу: Sequence Diagram для UC-05

**Гілка:** `lab-3-sequence-diagram`

**Створено:** 19.10.2026

**Статус:** Чернетка

**Вхідні дані:** UC-05 «Розіслати запити» із Завдання 2 (include UC-06 «Перевірити оплату першої половини») та ER-модель із Завдання 1.

## Намір

Показати динаміку UC-05 як sequence-діаграму: хто кого викликає, що повертається і де сценарій розгалужується. Реалізація, API і код поза межами роботи.

## Учасники

- **Mediator**: актор, людина. Запускає розсилку.
- **RequestService**: сервіс, який виконує логіку розсилки. У ER-моделі його немає, це уточнення цієї лаби.
- **Order**: сутність. Дає мовну пару (`source_language_id`, `target_language_id`) і статус.
- **Payment**: сутність. Перша половина (`type` = `first_half`), статус `paid` означає, що розсилати можна.
- **Translator**: сутність. Шукається за мовами, які знає (зв'язок Translator M:N Language).
- **Request**: сутність. Створюється зі статусом `pending` і `sent_at`.

## Кроки сценарію

1. Mediator викликає `sendRequests(orderId)`.
2. RequestService отримує Order і його мовну пару.
3. RequestService отримує Payment першої половини (UC-06).
4. Якщо статус не `paid`, розсилка зупиняється з помилкою.
5. RequestService шукає Translator, які знають обидві мови пари.
6. Якщо таких немає, жоден Request не створюється, Mediator отримує повідомлення.
7. Для кожного Translator перевіряється, чи вже є Request на цю пару `order_id` + `translator_id`. Якщо немає, створюється Request зі статусом `pending`.
8. Order отримує статус `sent_to_translators`, Mediator отримує кількість створених запитів.

## Альтернативні гілки

- `alt`: перша половина не оплачена.
- `alt`: немає перекладачів, які знають обидві мови.
- `loop`: запит кожному знайденому перекладачу.
- `opt`: дубль пари `order_id` + `translator_id` пропускається.

## Критерії прийняття

- **SC-001**: Кроки діаграми збігаються з основним потоком UC-05 і UC-06.
- **SC-002**: Кожен учасник-сутність має назву з ER-моделі посимвольно.
- **SC-003**: Є щонайменше одна гілка `alt`, `opt` і `loop`.
- **SC-004**: Кожен виклик має return-повідомлення.
- **SC-005**: Статус після розсилки збігається зі значенням `sent_to_translators` зі `spec.md` лаби 1.

## Припущення

- Розсилка можлива лише для Order зі статусом `created` і сплаченою першою половиною.
- Перша половина сплачується при створенні замовлення, тому в цьому сценарії Payment Service не бере участі.
- Спілкування між учасниками поза системою не моделюється.
- RequestService додано як шар логіки, окремої сутності в моделі даних він не має.
- Статуси Order за моделлю змінює Mediator, тому крок 8 є розбіжністю D-6, яку записано в аудиті.
