# Вимоги (EARS): розсилка запитів (UC-05)

Назви сутностей, атрибутів і статусів як у моделі Завдання 1. Вимоги написані під сценарії G01–G05 з `gherkin/scenarios.feature`. Вимоги до решти UC у цій ітерації не деталізуються (перша версія FR-001…FR-032 лишилась в історії, коміт 3b5ca19).

## Функціональні вимоги

- **FR-001** [Unwanted]: ЯКЩО Payment `first_half` Order не має статусу `paid`, ТО система ПОВИННА відхилити розсилку і не створювати Request. (G02)
- **FR-002** [Unwanted]: ЯКЩО Order має статус, відмінний від `created` і `sent_to_translators`, ТО система ПОВИННА відхилити розсилку. (G05)
- **FR-003** [Event-driven]: КОЛИ Mediator розсилає запити для Order з оплаченим Payment `first_half`, система ПОВИННА створити Request зі статусом `pending` для кожного Translator, який знає і `source_language_id`, і `target_language_id` і ще не має Request для цього Order. (G01, G04)
- **FR-004** [Event-driven]: КОЛИ після розсилки Order має хоча б один Request, система ПОВИННА встановити Order статус `sent_to_translators`. (G01, G04)
- **FR-005** [Ubiquitous]: Система ПОВИННА зберігати не більше одного Request на пару `order_id` + `translator_id`. (G04)
- **FR-006** [Unwanted]: ЯКЩО жоден Translator не знає обох мов пари Order, ТО система ПОВИННА не створювати Request, залишити статус Order без змін і показати Mediator повідомлення, що підходящих перекладачів немає. (G03)

## Системні перевірки, винесені з UC

Перевірка оплати першої половини перед розсилкою (раніше UC-06) — це FR-001. Перевірка другої оплати перед видачею результату (раніше UC-13) — вимога до UC «Отримати результат», у цій ітерації не деталізується.

## Нефункціональні вимоги

Не входять до діаграми й матриці трасування.

- **NFR-01 Користувачі й пристрої.** Mediator працює з комп'ютера, ширина екрана від 1280 px. Client, Translator і Editor працюють з комп'ютера або телефона, ширина екрана від 360 px. Підтримувані браузери: Chrome, Firefox, Edge, Safari — поточна і попередня версії.
- **NFR-02 Файл.** Система ПОВИННА приймати лише .docx розміром до 20 МБ і до 50 000 слів. Більший файл відхиляється з повідомленням про ліміт.
- **NFR-03 Навантаження.** Система ПОВИННА витримувати до 100 одночасних користувачів і до 500 нових Order на добу без порушення NFR-04.
- **NFR-04 Час відгуку.** Розсилка запитів (UC-05) для пари з ≤200 підходящих Translator ПОВИННА завершуватись за ≤3 с (95-й перцентиль). Відкриття сторінки статусу Order — за ≤1 с (95-й перцентиль). Профіль вимірювання: 50 одночасних запитів, тестова БД з 1000 Translator і 10 000 Order, сервер 2 vCPU / 4 ГБ RAM.
- **NFR-05 Мова.** Інтерфейс і повідомлення — українською. Дати — у форматі ДД.ММ.РРРР.
- **NFR-06 Безпека доступу до результату.** Результат доступний лише Client-власнику Order, призначеному Editor і Mediator цього Order. Передача даних лише по HTTPS (TLS 1.2+). Посилання на завантаження результату діє 15 хвилин. Сесія завершується після 30 хвилин без активності.
- **NFR-07 Технологія.** Веб-застосунок із реляційною БД. Унікальність пари `order_id` + `translator_id` (FR-005) забезпечується обмеженням у схемі БД.
