# Request як асоціативна сутність між Order і Translator

* Статус: accepted

* Дата: 2026-09-29

## Контекст і постановка проблеми

Одне замовлення може бути надіслане кільком перекладачам, а кожен
перекладач може прийняти або відхилити запит. Сам зв'язок між Order
і Translator має власні атрибути: статус запиту та дати його
надсилання і відповіді.

Потрібно визначити, як змоделювати зв'язок Order ↔ Translator,
не втрачаючи інформацію про окремі запити.

## Критерії прийняття рішення

* Зберігати кожен окремий запит перекладачу.

* Зберігати status, sent_at та responded_at.

* Підтримувати багато перекладачів для одного Order.

* Не створювати непотрібні дубльовані дані.

* Відповідати вимозі, що асоціативна сутність використовується,
  коли зв'язок має власні атрибути.

## Розглянуті варіанти

* Зберігати `translator_id` безпосередньо в Order.

* Створити Request як асоціативну сутність між Order і Translator.

* Створити окрему сполучну таблицю без власних атрибутів.

## Результат рішення

Обраний варіант: "Створити Request як асоціативну сутність між Order
і Translator", оскільки сам зв'язок має власні атрибути та повинен
зберігати історію запитів різним перекладачам.

Перекладач конкретного замовлення визначається через єдиний Request
зі статусом `accepted`.

Для одного Order та Translator пара `(order_id, translator_id)`
повинна бути унікальною. Для одного Order дозволено не більше одного
Request зі статусом `accepted`.

### Позитивні наслідки

* Зберігаються всі запити перекладачам.

* Можна розрізняти `pending`, `accepted` та `rejected`.

* Зберігаються дати надсилання та відповіді.

* `Order` не містить дубльованого `translator_id`.

* Модель відповідає вимозі про асоціативну сутність.

### Негативні наслідки

* Для визначення перекладача замовлення потрібно звертатися до Request
  зі статусом `accepted`.

* Обмеження "не більше одного accepted Request" є бізнес-правилом,
  яке не виражається звичайною кардинальністю ER-зв'язку.

## Переваги та недоліки варіантів

### Зберігати `translator_id` у Order

* Перевага, оскільки перекладач легко визначається без Request.

* Недолік, оскільки неможливо коректно зберігати кілька запитів
  різним перекладачам.

* Недолік, оскільки втрачаються статуси та дати окремих запитів.

### Request як асоціативна сутність

* Перевага, оскільки підтримує M:N зв'язок Order ↔ Translator.

* Перевага, оскільки зв'язок має власні атрибути.

* Перевага, оскільки зберігається історія запитів.

### Сполучна таблиця без власних атрибутів

* Перевага, оскільки моделює M:N зв'язок.

* Недолік, оскільки не має місця для status, sent_at та responded_at.
