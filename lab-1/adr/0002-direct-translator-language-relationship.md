# Прямий M:N зв'язок між Translator і Language

* Статус: accepted

* Дата: 2026-09-29

## Контекст і постановка проблеми

Один перекладач може знати багато мов, а одна мова може бути відома
багатьом перекладачам. Для цієї інформації потрібно змоделювати
зв'язок Translator ↔ Language.

Цей зв'язок не має власних атрибутів, тому потрібно визначити,
чи потрібна для нього окрема асоціативна сутність.

## Критерії прийняття рішення

* Зберігати, які мови знає кожен Translator.

* Представити M:N зв'язок між Translator і Language.

* Не створювати асоціативну сутність без власних атрибутів.

* Відповідати SC-004.

## Розглянуті варіанти

* Прямий M:N зв'язок Translator ↔ Language.

* Асоціативна сутність TranslatorLanguage.

* Зберігати список мов безпосередньо в Translator.

## Результат рішення

Обраний варіант: "Прямий M:N зв'язок Translator ↔ Language",
оскільки зв'язок не має власних атрибутів, а специфікація прямо
вимагає показувати його без сполучної таблиці.

### Позитивні наслідки

* Модель залишається простішою.

* Не створюється зайва сутність.

* ER-модель відповідає SC-004.

* Можна визначити, чи знає Translator потрібні для Order мови.

### Негативні наслідки

* Сам зв'язок не може зберігати додаткові атрибути без зміни моделі.

## Переваги та недоліки варіантів

### Прямий M:N зв'язок

* Перевага, оскільки відповідає вимозі специфікації.

* Перевага, оскільки не створює зайвої сутності.

* Перевага, оскільки зв'язок не має власних атрибутів.

### TranslatorLanguage

* Перевага, оскільки дозволив би додавати атрибути до зв'язку.

* Недолік, оскільки таких атрибутів наразі немає.

* Недолік, оскільки суперечить SC-004.

### Список мов у Translator

* Недолік, оскільки порушує нормалізовану структуру даних.

* Недолік, оскільки створює повторювану групу значень.
