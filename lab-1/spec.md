# Специфікація функціоналу: ER-модель домену Tlumach

**Гілка:** `lab-1-er-model`

**Створено:** 29.09.2026

**Статус:** Чернетка

**Вхідні дані:** Опис від користувача: "Змоделювати дані платформи Tlumach для замовлення перекладів. Client завантажує документ .docx, обирає мовну пару (мову оригіналу та ту, що потрібно перекласти) і створює замовлення. Mediator розсилає запити перекладачам, які знають мову замовлення. Translator приймає або відхиляє запит, виконує переклад та веде комунікацію разом з Mediator за потреби. Editor редагує результат. Оплата ділиться на дві частини по 50% (яка обраховується, дивлячись на кількість слів у Document). Потрібно описати детальніше сутності, атрибути, ключі, зв'язки та кардинальності."

## Намір

Описати дані платформи Tlumach як ER-модель: сутності, атрибути, первинні та зовнішні ключі, зв'язки з кардинальностями. Фізична схема БД (SQL DDL, ORM) поза межами роботи, не потрібна при виконанні.

## Ключові сутності

Усі `id` та зовнішні ключі мають тип `int`.

- **Client**: замовник. `id` (PK), `full_name`, `email`.
- **Translator**: виконавець. `id` (PK), `full_name`, `email`.
- **Editor**: редактор. `id` (PK), `full_name`, `email`.
- **Mediator**: посередник, контролює замовлення. `id` (PK), `full_name`, `email`.
- **Language**: довідник мов, кастомних мов немає. `id` (PK), `code`, `name`.
- **Document**: завантажений client файл .docx. `id` (PK), `file_name`, `word_count` (рахується автоматично), `uploaded_at`.
- **Order**: центральна сутність. `id` (PK), `client_id` (FK), `mediator_id` (FK), `editor_id` (FK, порожнє до призначення редактора), `document_id` (FK), `source_language_id` (FK), `target_language_id` (FK), `rate_per_word` (фіксується при створенні), `status`, `created_at`, `result_file_name` (порожнє до завершення редагування), `result_uploaded_at` (порожнє до завершення редагування). Перекладач замовлення не зберігається в Order: це `translator_id` єдиного Request зі статусом `accepted`.
- **Request**: пропозиція перекладачу виконати замовлення (асоціативна сутність між Order і Translator, бо має власні атрибути). `id` (PK), `order_id` (FK), `translator_id` (FK), `status` (`pending` / `accepted` / `rejected`), `sent_at`, `responded_at`.
- **Payment**: одна з двох частин оплати. `id` (PK), `order_id` (FK), `type` (`first_half` / `second_half`), `status` (`pending` / `paid` / `refunded` / `overdue`), `due_date`, `paid_at`. Сума не зберігається: вона обчислюється як 50% ціни замовлення.

**Статуси Order:** `created`, `sent_to_translators`, `in_progress`, `in_editing`, `ready`, `confirmed`, `closed`, `cancelled`.

**Значення статусів Order:**

- `created`: замовлення створене клієнтом. Перша половина оплати сплачується при створенні, запити перекладачам розсилаються лише після її сплати.
- `sent_to_translators`: Mediator розіслав запити.
- `in_progress`: один із запитів прийнято, перекладач працює.
- `in_editing`: Mediator призначив Editor, іде редагування.
- `ready`: редагування завершене, замовлення чекає другої оплати.
- `confirmed`: друга половина сплачена, Mediator підтвердив оплату й видав результат клієнту.
- `closed`: Mediator закрив замовлення після видачі результату.
- `cancelled`: замовлення скасоване (див. граничні випадки).

## Зв'язки

- Client 1:N Order. Mediator 1:N Order.
- Order має 0..1 Editor (до призначення немає), Editor має 0..N Order. Mediator призначає Editor, коли перекладач завершив роботу.
- Document 1:1 Order.
- Language 1:N Order двічі: `source_language_id` і `target_language_id`.
- Translator M:N Language ("знає мови"), без власних атрибутів, тому без сполучної таблиці.
- Order 1:N Request. Translator 1:N Request. Разом це зв'язок Order M:N Translator через асоціативну сутність Request. Не більше одного Request на Order має статус `accepted`.
- Order 1:N Payment (не більше двох: перша та друга половина).

## Функціональні вимоги

- **FR-001**: Система ПОВИННА зберігати замовлення з клієнтом, посередником, документом і мовною парою.
- **FR-002**: Ціна замовлення ПОВИННА обчислюватися як `word_count` × `rate_per_word`, а не зберігатися окремим полем.
- **FR-003**: Система ПОВИННА зберігати, які мови знає кожен перекладач.
- **FR-004**: Система ПОВИННА зберігати кожен запит перекладачу зі статусом і датами. Пара `order_id` + `translator_id` в Request ПОВИННА бути унікальною: один перекладач отримує не більше одного запиту на замовлення.
- **FR-005**: Система ПОВИННА зберігати кожну половину оплати окремим записом зі строком оплати. Сума кожної половини обчислюється як 50% ціни замовлення і не зберігається.
- **FR-006**: Замовлення ПОВИННО мати не більше одного прийнятого запиту. Перекладач замовлення визначається через цей запит.
- **FR-007**: Запити ПОВИННІ надсилатися лише перекладачам, які знають обидві мови пари (`source_language_id` і `target_language_id`).
- **FR-008**: `source_language_id` ПОВИНЕН відрізнятися від `target_language_id`.
- **FR-009**: Система ПОВИННА зберігати результат перекладу після редагування (`result_file_name`, `result_uploaded_at`). Результат видається клієнту лише після сплати другої половини.

## Граничні випадки

- Ніхто не взявся за переклад: замовлення отримує статус `cancelled`, перша половина оплати отримує статус `refunded`.
- Друга половина не сплачена до `due_date`: друга половина отримує статус `overdue`, Mediator зв'язується з клієнтом. Якщо клієнт не відповідає протягом N днів після `due_date`, замовлення отримує статус `cancelled`, а перша половина залишається платформі (як компенсація за втрачений час).
- Потрібної мови для мовної пари немає в довіднику: посередник додає її, коли з'являється перекладач, який її знає.

## Критерії прийняття

- **SC-001**: Усі `id` та зовнішні ключі мають тип `int`.
- **SC-002**: Модель у 3НФ: немає повторюваних груп, похідних даних і транзитивних залежностей.
- **SC-003**: Кожен зв'язок має явну кардинальність.
- **SC-004**: Translator M:N Language показано як зв'язок без сполучної таблиці; асоціативна сутність лише Request.

## Припущення

- Приймається лише формат .docx.
- Одне замовлення має одну пару мов.
- Оплата завжди у два етапи по 50%.
- Спілкування між Client, Translator, Editor і Mediator (зокрема передача результату редактора перекладачу) відбувається поза системою і не моделюється.
- Кількість днів N до скасування є налаштуванням платформи, а не даними замовлення. Строк оплати для кожного платежу зберігається в `Payment.due_date`.
- Статуси Order змінює Mediator.
- Mediator призначається замовленню платформою автоматично під час створення, тому `Order.mediator_id` обов'язковий.
- Мови Editor не моделюються: Mediator сам обирає редактора, який підходить для замовлення.
- Для першої половини оплати `Payment.due_date` дорівнює даті створення замовлення, бо вона сплачується при створенні.
