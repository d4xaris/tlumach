# Промпт #2: Генератор ER-діаграми з `spec.md`

**Модель ШІ:** Claude Sonnet 5.5 (Anthropic)

## Промпт

```text
Ти допомагаєш побудувати ER-діаграму для домену Tlumach на основі готової специфікації `spec.md`.

ВХІД

Я надаю тобі повний текст `spec.md`.

Твоє завдання — побудувати ER-діаграму, яка ТОЧНО відповідає специфікації.

ПРАВИЛА

- Не вигадуй нових сутностей, атрибутів, зв'язків або правил, яких немає у `spec.md`.
- Не видаляй сутності, атрибути або зв'язки, які явно описані в `spec.md`.
- Перед побудовою діаграми перевір специфікацію повністю.
- Якщо між різними розділами `spec.md` є суперечність, не вигадуй рішення самостійно: вкажи суперечність окремо.
- Назви сутностей та атрибутів на діаграмі мають точно відповідати назвам у `spec.md`.
- Усі PK і FK повинні бути явно позначені.
- Для кожного зв'язку покажи кардинальність.
- Обов'язково розрізняй `1:1`, `1:N`, `M:N`, `0..1` та `0..N`, якщо вони вказані у специфікації.
- Обов'язковість/необов'язковість FK має бути відображена відповідно до `spec.md`.
- Не додавай фізичні деталі БД, яких немає у специфікації.
- Типи `id` та FK покажи як `int`, оскільки це визначено специфікацією.
- Не перетворюй зв'язок `Translator M:N Language` на додаткову сутність, якщо цього немає у `spec.md`.
- `Request` залиш як асоціативну сутність між `Order` і `Translator`.
- Не додавай `translator_id` до `Order`, оскільки специфікація прямо визначає перекладача через прийнятий `Request`.
- Не додавай `amount` до `Payment`, оскільки сума оплати є похідним значенням.
- Не додавай до моделі поле для N днів до скасування, оскільки це налаштування платформи, а не дані замовлення.

ЩО МАЄ БУТИ НА ДІАГРАМІ

Покажи всі сутності зі специфікації:

- Client
- Translator
- Editor
- Mediator
- Language
- Document
- Order
- Request
- Payment

Для кожної сутності покажи:
- назву;
- усі атрибути;
- PK;
- FK;
- допустимі значення для status/type, якщо вони є важливими для розуміння моделі.

ОСНОВНІ ЗВ'ЯЗКИ

Обов'язково відобрази:

- Client 1:N Order
- Mediator 1:N Order
- Order 0..1 : 0..N Editor
- Document 1:1 Order
- Language 1:N Order через `source_language_id`
- Language 1:N Order через `target_language_id`
- Translator M:N Language
- Order 1:N Request
- Translator 1:N Request
- Order M:N Translator через Request
- Order 1:N Payment, максимум два Payment на Order

Для зв'язків через FK покажи відповідні FK без дублювання сутностей.

ОСОБЛИВІ ОБМЕЖЕННЯ

На діаграмі або в окремій примітці явно вкажи:

- `Order` має не більше одного `Request` зі статусом `accepted`.
- Перекладач замовлення визначається через `Request.translator_id`, де `Request.status = accepted`.
- `Request(order_id, translator_id)` є унікальною парою.
- `source_language_id != target_language_id`.
- `Payment` має не більше двох записів для одного `Order`: `first_half` і `second_half`.
- `Payment` не має поля `amount`.
- `Order` не має поля `translator_id`.

ФОРМАТ ДІАГРАМИ

Створи ER-діаграму у Mermaid ER diagram або іншому текстовому форматі, який можна зберігати в GitHub і відтворити без ручного малювання.

Якщо Mermaid ER не дозволяє точно відобразити певне обмеження або кардинальність, залиш основну ER-діаграму коректною, а обмеження додай окремими примітками.

ПІСЛЯ ДІАГРАМИ

Додай короткий розділ "Перевірка відповідності spec.md":

1. Переліч усі сутності, які є на діаграмі.
2. Переліч усі зв'язки та їхні кардинальності.
3. Перевір наявність усіх PK і FK.
4. Перевір, що `Order.translator_id` відсутній.
5. Перевір, що `Payment.amount` відсутній.
6. Перевір, що N днів до скасування не змодельовано як атрибут.
7. Перевір, що `Request` є єдиною асоціативною сутністю.
8. Вкажи будь-які невідповідності між діаграмою та `spec.md`.

Не змінюй `spec.md` самостійно. Якщо для коректної діаграми потрібна зміна специфікації, спочатку окремо опиши проблему та запропонуй зміну.
```

## Що має бути результатом

* ER-діаграма, що відповідає `spec.md`.
* Усі 9 сутностей.
* PK/FK та кардинальності.
* Окремі примітки для обмежень, які не можна коректно передати засобами ER-нотації.
* Коротка перевірка відповідності діаграми специфікації.
