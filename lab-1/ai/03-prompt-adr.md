# Промпт #3: Генератор ADR для ER-моделі Tlumach

**Модель ШІ:** Claude Sonnet 5.5 (Anthropic)

## Промпт

```text
Ти допомагаєш документувати архітектурні та модельні рішення для домену Tlumach у форматі ADR (Architecture Decision Record).

ВХІД

Я надаю тобі:

1. Повний текст `spec.md`.
2. Поточну ER-діаграму.
3. Результати аудиту ER-моделі або опис конкретного рішення, яке потрібно задокументувати.

Твоє завдання — створити ADR, який точно документує прийняте рішення та його обґрунтування.

ПРАВИЛА

- Не вигадуй проблем, вимог або обмежень, яких немає у `spec.md`, ER-моделі або результатах аудиту.

- Не змінюй `spec.md` та ER-модель самостійно.

- ADR повинен документувати рішення, а не замінювати специфікацію.

- Чітко розділяй:
  - контекст і проблему;
  - критерії прийняття рішення;
  - розглянуті варіанти;
  - прийняте рішення;
  - позитивні та негативні наслідки.

- Прийняте рішення повинно бути безпосередньо пов'язане з вимогами домену Tlumach.

- Не додавай у ADR рішення, яких фактично не було прийнято.

- Не використовуй ADR для опису очевидних технічних деталей, якщо вони не є окремим модельним рішенням.

- Якщо надані матеріали суперечать один одному, не вигадуй рішення самостійно. Окремо вкажи суперечність і запропонуй, що потрібно уточнити у `spec.md`.

- Якщо рішення вже явно визначене у `spec.md`, ADR повинен пояснювати причину цього рішення, а не змінювати його.

- Не додавай фізичні деталі БД, яких немає у специфікації.

- Не додавай SQL, ORM-моделі або DDL.

- Використовуй точні назви сутностей та атрибутів із `spec.md`.

- Якщо рішення стосується кардинальності, PK/FK, асоціативної сутності або похідного атрибута, явно поясни, як це рішення впливає на ER-модель.

- Якщо рішення стосується нормалізації, поясни, яке дублювання або залежність воно усуває.

- Якщо рішення стосується бізнес-правила, відокремлюй саме правило домену від способу його представлення в ER-моделі.

ФОРМАТ ADR

Створи ADR у форматі Markdown.

Файл повинен мати назву:

`NNNN-short-title-with-dashes.md`

де `NNNN` — порядковий номер ADR.

Наприклад:

`0001-request-as-associative-entity.md`

Структура ADR:

# Назва рішення

* Статус: accepted

* Дата: 2026-09-29

## Контекст і постановка проблеми

Опиши, яку проблему або модельне питання потрібно було вирішити.

Поясни, чому це питання важливе для ER-моделі Tlumach.

## Критерії прийняття рішення

Переліч конкретні вимоги, яким повинно відповідати рішення.

Критерії повинні випливати з `spec.md`, acceptance criteria або результатів аудиту.

## Розглянуті варіанти

Переліч альтернативні способи моделювання.

Для кожного варіанта коротко поясни його суть.

## Результат рішення

Чітко зафіксуй прийняте рішення.

Поясни, чому саме цей варіант відповідає вимогам.

Якщо рішення впливає на ER-модель, явно вкажи:

- які сутності використовуються;
- які атрибути залишаються або не додаються;
- які зв'язки використовуються;
- яка кардинальність застосовується;
- які PK/FK або обмеження мають значення.

### Позитивні наслідки

Переліч переваги прийнятого рішення для моделі та відповідності специфікації.

### Негативні наслідки

Переліч обмеження або компроміси прийнятого рішення.

## Переваги та недоліки варіантів

Для кожного розглянутого варіанта окремо вкажи:

### Назва варіанта

* Перевага: ...

* Недолік: ...

## Посилання

Вкажи конкретні місця у `spec.md`, acceptance criteria або результати аудиту, на яких ґрунтується рішення.

Наприклад:

* `spec.md`: FR-004.
* `spec.md`: FR-006.
* `spec.md`: SC-004.

ПРАВИЛА ДЛЯ КІЛЬКОХ ADR

Якщо потрібно створити декілька ADR, кожне рішення повинно бути окремим файлом.

Не об'єднуй незалежні рішення в один ADR.

Не створюй окремий ADR для кожної дрібної зміни атрибута.

Окремий ADR потрібен тоді, коли є самостійне модельне рішення, для якого існували альтернативи або яке важливо пояснити під час захисту.

Для домену Tlumach потенційними рішеннями можуть бути:

1. `Request` як асоціативна сутність між `Order` і `Translator`.

2. Прямий M:N зв'язок між `Translator` і `Language` без окремої асоціативної сутності.

3. Не зберігати похідний `Order.price`, якщо ціна визначається як `word_count × rate_per_word`.

4. Не зберігати `Payment.amount`, якщо кожна частина платежу визначається як 50% ціни Order.

Не створюй ADR для цих рішень автоматично, якщо вони не відповідають фактичним рішенням у наданих матеріалах.

ПЕРЕВІРКА ADR

Після тексту ADR додай короткий розділ "Перевірка ADR":

1. Вкажи, яку проблему вирішує ADR.

2. Вкажи, яке рішення прийнято.

3. Вкажи, які альтернативи були розглянуті.

4. Перевір, що рішення не суперечить `spec.md`.

5. Перевір, що всі згадані сутності та атрибути існують у `spec.md`.

6. Перевір, що ADR не додає нових вимог або сутностей.

7. Вкажи конкретні FR/SC або інші частини `spec.md`, які підтверджують рішення.

8. Якщо є невідповідність між ADR та `spec.md`, не виправляй її самостійно, а явно вкажи її.

ВАЖЛИВО

ADR не повинен бути описом усієї ER-моделі.

ADR документує конкретне рішення та причину його прийняття.

Не використовуй ADR для дублювання всього вмісту `spec.md`.
```

## Що має бути результатом

* Один або декілька ADR-файлів у форматі Markdown.

* Кожен ADR описує окреме важливе рішення щодо ER-моделі Tlumach.

* Для кожного рішення вказано контекст, проблему, критерії прийняття рішення та розглянуті альтернативи.

* Прийняте рішення чітко зафіксоване та обґрунтоване на основі `spec.md`, ER-моделі або результатів аудиту.

* Вказані позитивні та негативні наслідки прийнятого рішення.

* Кожен ADR містить посилання на відповідні FR, SC або інші частини `spec.md`.

* ADR не додає нових сутностей, атрибутів, зв'язків або правил, яких немає у специфікації.

* ADR не замінює `spec.md` та не містить фізичної схеми БД.

* Для кожного ADR виконано коротку перевірку відповідності `spec.md`.

* Якщо між ADR, ER-моделлю та `spec.md` є суперечність, вона явно вказана, а не виправлена автоматично.
